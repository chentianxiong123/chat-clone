# 记忆库 vs 知识库分离 · 存储架构决策

> 日期：2026-11-07
> 结论：live 上下文用 `pi-agent-core` 内存数组；记忆存储用自建 SQLite（纯归档，不回灌上下文）；RAG 知识库保持独立不动。

## 一、核心区分：知识库 ≠ 记忆库

| | 知识库（RAG） | 记忆库（待建） |
|---|---|---|
| 本质 | **静态参考库** | **动态增长** |
| 诞生时机 | **agent 创造以前**就存在 | agent **运行中长出来** |
| 内容 | 多年聊天记录提炼的风格/口癖/知识 | ongoing 会话历史 + `remember` 记的朋友事实/约定 |
| 用途 | `search_past_memory` 查"本人当年怎么说"，学语气 | 回忆"上次聊了啥/朋友喜好/约定" |
| 存储 | `qwen_persona_rag.sqlite`（chunks_fts 17846 行，已建） | **新建**，本档定义 |
| 是否回灌 live 上下文 | 否（工具按需查） | **否（纯归档，只写不读回）** |

**关键**：两者是**独立的两套系统**，别混。RAG 是"出生前的参考书"，记忆库是"活着长出来的经历"。

## 二、三层架构

```
┌─ live 上下文 ──────────────┐
│  pi-agent-core: messages[] │  ← 内存数组，喂模型的就这个
│  transformContext 裁剪      │     reset() 清空（保留 system baseline）
│  convertToLlm 转格式        │     不持久化、不碰 DB
└────────────┬───────────────┘
             │ 每轮结束 append（只写）
             ▼
┌─ 记忆库（新建 SQLite）─────┐
│  会话历史 + remember 事实    │  ← 纯归档，永不回灌 live 上下文
│  FTS5 关键词 + 向量 blob     │     将来"回忆上次聊啥"单独查它
│  按 scene_key 分群/私聊      │
└────────────────────────────┘

┌─ 知识库（现有 RAG，不动）──┐
│  qwen_persona_rag.sqlite    │  ← 静态，search_past_memory 查
│  chunks_fts + qwen 向量     │     学风格/口癖，与记忆库无关
└────────────────────────────┘
```

## 三、存储选型：为什么 SQLite（自建），不用 pi-durable / jsonl

### pi-durable — 不用
- **Experimental，API 随版本变** → 生产聊天机器人架上面有风险
- 拖 `chord` 对象运行时，依赖重
- per-conversation 模型，套 chat-clone 的 scene_key（群/私聊多场景）要改
- 持久化能力自己 20 行 SQLite append 就替代

### jsonl — 不用（做存储后端）
- **无索引**：每次搜全文件扫（grep）或全量进内存，数据大了慢
- 中文 grep 无分词，易漏；FTS5 有分词
- 存不了向量 blob → 做不了语义召回
- 唯一优势（人类可读/git diff）对聊天存储用不上

### SQLite（自建）— 采用
- **FTS5 全文索引**：毫秒级关键词搜 + bm25 排序，中文分词 ✓
- **向量存 blob**（配 sqlite-vec）：语义召回能做
- 单文件、事务、索引，贴合已有 RAG 那套机器
- 与 pi live 上下文解耦（上下文是内存数组，不碰存储），无配套顾虑

## 四、记忆库 SQLite 表设计（草案）

```sql
-- 会话消息（纯归档）
CREATE TABLE memory_message (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  scene_key TEXT NOT NULL,        -- 'g:群号' / 'p:好友号'
  role TEXT NOT NULL,             -- user / assistant
  who TEXT,                       -- 说话人昵称（群）
  content TEXT NOT NULL,
  ts INTEGER NOT NULL
);
CREATE INDEX idx_mem_scene_ts ON memory_message(scene_key, ts);
-- 关键词召回（将来"回忆上次聊啥"）
CREATE VIRTUAL TABLE memory_fts USING fts5(content, who, content='memory_message', rowid='id');

-- 事实/约定（remember 工具落这里）
CREATE TABLE memory_fact (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  scene_key TEXT NOT NULL,
  fact TEXT NOT NULL,
  ts INTEGER NOT NULL
);
```

- **只 append，不 UPDATE/DELETE（除手动清理）**
- **永不 SELECT 回灌 live 上下文**（上下文只走 pi-agent-core 内存数组）
- 召回是**独立查询**（"上次聊 X"→查 memory_fts），结果作为工具返回给模型，不是拼进 system

## 五、集成计划（pi-agent-core 当 LLM loop 内核）

1. `npm i @earendil-works/pi-agent-core`
2. chat-clone 手搓的 callLlm 循环（core.ts）→ 换 pi `Agent` 类
   - `streamFn` = 自己 fetch `agnes-2.5-flash` API（OpenAI 兼容 `LLM_BASE_URL`），不碰 pi-ai provider
   - `transformContext` = 取最近 maxContextTurns 轮
   - `convertToLlm` = ChatMessage → pi Message
3. 每个会话 = 一个 Agent 实例，`messages[]` 即 live 上下文
4. 攒批/mention/概率沉默 = pi 之上的 intake 层（喂 `agent.prompt()`），保留
5. 每轮结束把 user/assistant 消息 append 到 memory SQLite（纯归档）
6. `search_past_memory` 继续查 RAG 知识库；新增 `recall_memory`（可选）查记忆库
7. clear = `agent.reset()`（清内存上下文），记忆归档不受影响

## 六、待定 / 风险

- pi `Agent` 的 Message 类型 / 流式事件 → chat-clone ChatMessage 适配层工作量
- pi-durable 若转正（非 Experimental）可重评
- 记忆库召回（recall_memory）是否需要、优先级待定
