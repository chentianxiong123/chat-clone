# Agent 设计文档（v2：双触发条件）

> 状态：设计中（尚未实现）
> 日期：2026-08-18

## 一、设计原则

大部分逻辑砍掉，只保留核心。

| 砍掉 | 理由 |
|------|------|
| `timing.ts` 拟人延迟（3~60s） | 群友等太久体验差；逐条延迟无意义 |
| burst 25% 概率连发两条 | 伪随机制造混乱 |
| 夜晚节奏减半 | 无人在夜里测试 |
| 长回复拆两段发送 | 一段话不超过 20 字，无需拆 |

| 保留 | 理由 |
|------|------|
| RAG 搜索历史 | 接话的灵魂 |
| LLM 调用（agnes-2.0-flash） | 生成回复 |
| 重试 2 次 | API 不稳定 |

## 二、双触发条件（核心设计）

**原则：不逐条触发，攒批处理。**

```
群消息 ──→ buffer 攒积
              │
              ├─ 条件A：攒够 N=5 条 → 立即打包触发
              │
              └─ 条件B：距上一条超过 T=60s → 打包触发
```

- **密度高**（群聊活跃，连续来消息）：攒够 5 条触发一次，1 次 LLM 调用回 N 条消息
- **密度低**（冷清群）：来 1 条后 1 分钟没新消息，把这条单独打包触发
- 触发后 buffer 清空，回复**一条**完整的话

### 为什么这样设计

1. 每条消息触发一次太浪费：API 慢（10~20s/次）+ 不稳定（偶发 100s+ 卡死）
2. 攒够上下文再回，更接近真人——一次回应最近一段对话，而不是逐条回
3. 防抖（debounce）保证冷清群也能回消息

### 参数（可调）

| 参数 | 值 | 说明 |
|------|----|-----|
| `N`（数量阈值） | 5 | 攒够 5 条立即触发 |
| `T`（时间阈值） | 60s | 距上一条 60s 无新消息则触发 |
| 触发回复 | 1 条 | 廖风格本来就是短句堆叠 |

## 三、数据流

```
NapCat WS(3001) 推送群消息
   ↓
[过滤器] 自己发的消息 → 跳过
   ↓
buffer.push("昵称: 内容")
   ├─ 长度 ≥ N → flush()
   └─ 重置 60s 定时器 → 到期 flush()
   ↓
flush():
   ctx = buffer 清空取走
   rag = searchRag(ctx 全文)      ← 关键词 LIKE 搜索历史
   reply = callLlm(prompt, ctx)   ← agnes-2.0-flash
   ws.send(send_msg, reply)
```

## 四、触发钩子

钩子就是 NapCat 的 **WebSocket 事件推送**：

```json
{ "post_type": "message", "message_type": "group",
  "group_id": 719972557, "user_id": 123,
  "sender": { "nickname": "明月" }, "message": "在吗" }
```

- 事件来一条触发一次回调（轻量，仅入 buffer）
- **唯一过滤**：`sender.user_id == 自己` 则跳过（NapCat 会推自己的消息）
- 不需要轮询、不需要状态机

## 六、验证方式

离线测试（不接真实 QQ）：
1. 起假 WS 服务器模拟 NapCat，config 指向它
2. 灌入真实群友发言（从 chat_records 挖的）
